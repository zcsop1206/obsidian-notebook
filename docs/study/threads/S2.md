ASSUMED:
- Stages start at 0; the first event on a basic (`open`, mark, attempt, fog, drill, stage-set)
  sets stage 1 with the first drill due one stage-1 interval later (2 days, capped by deadline).
  A never-opened basic is never weak, never due, never rebuilt; it does block its track.
- A clean hold (held, no help, not given up) is a clean retrieval of each basic its methods are
  taught in (`methods.md` entry or a `basic/anchor` pair), once a day per basic like any result.
  Held after help, missed, blind, moot move no stage. Katas move no stage (devin's edit, kept).
- `used` ticks are what the item took; when empty, a problem falls back to its solution's
  `methods:` line. Method accuracy (p_id) counts hidden problem and kata settles only, smoothed,
  last 20; a later settle event for the same item only re-ticks (never re-rates).
- Reach comes from the item's latest `call` event (`reach: true`); the settle event has no field.
- Hooks: item `thm:<doc>#<theorem anchor>` (attempt n > 1: `#<n>` appended; the proof's anchor is
  accepted too). Each item is graded once; `nextHookItem()` names the next attempt. A hook moves
  the basic's stage and, with the proof's `(d x)`, the area rating at K 0.3; it never moves the
  stretch streaks and never counts toward p_id.
- Hidden picks: a problem is hidden-OK when its methods are known (solution line or tags row);
  "practised" means an opened basic in the area or a counted settle there; `gen` always is.
- Today: 3 problem slots over the areas of live tracks (nearest deadline first, round robin),
  every third slot hidden in a push area; one reach per area. One kata slot while any live track
  serves a kata (the asic track in practice); in push mode it is hidden one day in three (one
  slot cannot follow the 1-in-3 slot pattern). Drills: 2 under 45 minutes, 3 under 90, else 4;
  the engine doubles the minutes on Saturday, so callers pass `settings.minutes` as it is. The
  drill item is the basic's derive prompt drilled longest ago, else its first proof or theorem.
- Tracks: weight 0 ignored; a track is live until its deadline (a range until its end, with 0
  days left inside it); a track serves a doc when the doc's `tracks:` lists it, its areas include
  the doc's area, or its `docs` column matches (globs on ids; `basics`/`topics`/... restrict the
  folder). `next` is the nearest live dated track.
- Triage: lost in a basic -> rebuild-basic, unless one is pending (`requested`) or one landed and
  no graded retrieval came after it (then rationed). A weak linked basic rebuilds the same way.
  A pending rewrite on the passage -> `requested`. The rationed cycle starts at the first lost
  mark whose own triage was rationed, after the last easy/forgot/clear and after the passage's
  last rewrite request, and on a build newer than that request (and than a landed rebuild of the
  doc); ink = the latest `attempt` event's strokes since that mark. `since`/`eligibleAt` are ISO.
- Budget: rewrite requests on the doc made on a build newer than its last landed rebuild request
  (a topic has no rebuild path in the plugin, so its 3 last until the laptop lands one).
- A lost mark logged while the budget is spent pulls its drill forward to that day; a forgot
  mark pulls forward the basics the passage rests on (and the doc, if a basic).
- Open marks: the latest mark per passage, minus clears and lost marks a later landed rewrite (or
  a rebuild of the doc) answered.
- Store: events written this session stay in memory even if a reload misses them; a device name
  is cleaned to `[a-z0-9-]` with a trailing `-<digits>` joined (`ipad-2` -> `ipad2`) so it never
  reads as another device's log part.
